# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

"Taskflow OS" WhatsApp API — a FastAPI backend that turns WhatsApp Business into a sales channel. Merchants manage a product catalog and receive orders over WhatsApp; a Claude-powered AI ("Amara") negotiates prices and takes orders from customers in the same chat, using per-merchant product catalogs and optional knowledge-base documents. Payments/installments are handled via the Tunzaa payment provider. Login is passwordless OTP-over-WhatsApp (no passwords in this system despite the `hashed_password` field in seed scripts).

## Commands

Local dev (no Docker):
```bash
pip install -r requirements.txt
uvicorn main:app --host 0.0.0.0 --port 8000 --reload
```

Docker dev stack (API + Redis + Celery worker, with hot reload via bind mount):
```bash
docker compose up --build
```

Migrations (Alembic; `scripts/run.sh` runs `alembic upgrade head` automatically on container start):
```bash
alembic upgrade head
alembic revision --autogenerate -m "description"
```

Manual/exploratory testing — there is no pytest suite in this repo:
- `tests/whatsapp_api_tests.py` is a standalone script (run directly with `python tests/whatsapp_api_tests.py`) that hits the real Meta Graph API to sanity-check `whatsapp_business_management` / `business_management` permissions and webhook subscription. Requires real Meta credentials in `.env`.
- `scripts/simulate_whatsapp.py` — interactive CLI that simulates an inbound WhatsApp webhook against a locally running server (`http://localhost:8000`), then polls the DB for the AI's outbound reply. Use this to manually test the AI sales flow end-to-end without a real WhatsApp number.
- `scripts/seed_whatsapp_account.py` — seeds a dummy user + `WhatsAppAccount` row from `.env` (`PHONE_NUMBER_ID`/`WHATSAPP_TOKEN`) for local testing.

Production image build/run uses `Dockerfile.prod` (multi-stage, non-root `webapp` user, Gunicorn+Uvicorn workers via `app/core/gunicorn_conf.py`); `docker-compose.prod.yml` pulls the published `whoisladleo/whatsapp:latest` image. CI (`.github/workflows/docker-publish.yml`) builds `Dockerfile.prod` and pushes to Docker Hub as `whoisladleo/whatsapp-api` on every push to `master`.

## Architecture

**Request flow**: `main.py` wires up FastAPI, CORS, and mounts routers under `/api/v1` (`app/api/v1/*.py`): `auth`, `whatsapp`, `instagram`, `knowledge`, `tunzaa_webhook`, `accounts`, `products`, `orders`, `pool`. Static product images are served from `/static` (backed by `static/uploads/products`, or Cloudflare R2 when `R2_*` env vars are set).

**Multi-tenant model**: A `User` (merchant) owns one or more `WhatsAppAccount` rows (each tied to a Meta `phone_number_id` + access token). Most WhatsApp-account-scoped endpoints (`/whatsapp/messages`, `/whatsapp/messages/send`) resolve the account via the `get_whatsapp_account` dependency in `app/api/v1/whatsapp.py`, which accepts the account either as the `X-WhatsApp-Account-ID` / `X-Account-ID` header or query param — not from the JWT. Account-management endpoints (`/whatsapp/accounts*`) and everything under `/products`, `/knowledge` are scoped by the authenticated user (`get_current_user` in `app/api/deps.py`, JWT bearer via `PyJWT`).

**Number provisioning**: `POST /whatsapp/accounts` supports two paths. Bring-your-own-number (BYON): the merchant supplies their own `phone_number_id` + `access_token`, used as-is. Pool-assigned: both fields omitted, and a number is auto-claimed from `PhoneNumberPool` (`app/crud/whatsapp.py`'s `claim_available_pool_number` — an atomic conditional-`UPDATE` claim, not `SELECT ... FOR UPDATE`, so it's correct on both SQLite tests and Postgres prod) using the shared `settings.WHATSAPP_POOL_ACCESS_TOKEN`. Pool numbers are pre-provisioned in Meta Business Manager out-of-band (`scripts/add_pool_number.py` registers one as `AVAILABLE` after that manual Meta-side setup) — this is a provisioning pool, not a shared/multiplexed number: each business still gets a dedicated `phone_number_id` for the life of the account, so webhook routing is unaffected either way. Supplying exactly one of the two fields is a 400; an empty pool on an auto-assign request is a 409. Deleting an account releases its pool row (`RELEASED`, not immediately reusable) via `release_pool_number_for_account`.

**Auth**: a single login method, not password-based, issuing the JWT (`sub` = user id, `app/core/security.py`). OTP-based: `/auth/request-otp` creates the user if needed and sends a 6-digit OTP to their WhatsApp number using the platform's *default* `WhatsAppProvider` (from `settings.WHATSAPP_TOKEN`/`PHONE_NUMBER_ID`, not the merchant's own account); `/auth/verify-otp` checks it and issues the JWT. The OTP template send (`send_otp_message`, `app/api/v1/auth.py`) is sent with `language_code=settings.WHATSAPP_OTP_TEMPLATE_LANGUAGE` (default `en`) — Meta templates are keyed by `(name, language)`, and a template the WhatsApp Manager UI *displays* as "English" is commonly registered under the bare `en` code, not `en_US`; sending the wrong one fails with error 132001 ("template name does not exist in `<language>`") even though the template exists and is approved. Check the template's actual registered code in WhatsApp Manager before changing this setting, not just its display name. The OTP button is sent as a `url`-type button (`sub_type: "url"`, `parameters: [{"type": "text", "text": otp}]`), not the dedicated `copy_code` sub_type its "Copy code" label in the Manager UI implies — confirmed live via Meta error 132018 ("Button at index 0 must be of type Url"); some authentication templates are still registered this way under the hood regardless of what the UI shows. There's no per-customer language detection for the OTP send itself (a login request has no prior conversation to infer one from) — `_otp_fallback_message` keeps the plain-text fallback in the same language as `WHATSAPP_OTP_TEMPLATE_LANGUAGE` so the two stay consistent, but this is a single global default, not per-user; customer-facing templates elsewhere (e.g. order reminders) are a separate question since a customer's conversation history is a real signal, unlike a fresh login attempt.

**Inbound webhook pipeline** (`POST /whatsapp/webhook` in `app/api/v1/whatsapp.py`):
1. `WebhookParser.parse_inbound` (`app/core/webhook_parser.py`) flattens Meta's nested webhook JSON into simplified message/status dicts.
2. The account is looked up by `phone_number_id`; message/status is persisted via `app/crud/message.py`.
3. Routing: if the sender's phone number matches the account owner's `username` (merchants log in with their phone number as username), the message is treated as a **merchant command** and goes to `handle_merchant_message` (`app/services/merchant_handler.py`) — regex-parsed slash commands (`/stock`, `/out_of_stock`, `/price`, `/manage`, `/resume`, `/reply`) that mutate `Product` rows or relay a manual reply directly. Otherwise, if `account.ai_enabled`, it's routed to `llm_service.generate_response` (`app/services/llm.py`) as a **customer** message.
4. The AI reply (or merchant command reply) is sent back via `WhatsAppProvider.send_text` and logged as an outbound `Message`.
5. If `account.callback_url` is set, the raw parsed webhook item is also forwarded there (best-effort, failures swallowed).

**AI sales engine** (`app/services/llm.py`, `LLMService`, backed by the `anthropic` SDK / Claude): per customer phone number it tracks a `Customer` + `ConversationContext` (state machine: `NEGOTIATING` → `HUMAN_HANDOFF` / `MANAGEMENT`). When `context.state == HUMAN_HANDOFF`, the AI stays silent so a human can take over. There's a special-cased "platform account" (`account.name.lower() == 'taskflow'`) where the *merchant themselves* is treated as the counterparty for onboarding rather than a customer — look here first if AI behavior seems wrong for a specific account. The AI's product catalog comes from `Product` rows filtered by `merchant_id`; optional markdown knowledge base content can come either from a `KnowledgeBase` DB row (`app/crud/knowledge.py`, looked up via `account.product_slug`) or a static file at `knowledge/{product_slug}.md` (`LLMService._get_knowledge_base`) — these are two separate, not-yet-unified mechanisms. All prices (`Product.max_price`/`min_price`, and the platform pitch's fixed subscription price) are plain numbers with no currency unit stored anywhere — the catalog string built for the model explicitly labels every price `TZS {price:,.0f}` and every prompt (all three: WhatsApp `generate_response`, `generate_comment_reply`, `generate_dm_response`) has an explicit RULES line forbidding `$`/USD/any other currency or conversion. This was a real production incident — with no currency label at all, the model was observed live quoting a 100,000 TZS price as "$100,000" to a real Instagram prospect (a ~250,000x error). Don't remove the `TZS`-labeling or the currency RULES line from any of the three prompts, and add the same to any new one.

**Payments** (`app/services/tunzaa.py`, `TunzaaService`): wraps the Tunzaa API for mobile-money push payments and "Lipa kwa Awamu" (pay-in-installments) plans, tied to `Order`/`Installment` models. Auth token is cached in-process with a 55-minute TTL. `app/api/v1/tunzaa_webhook.py` receives payment/installment status callbacks from Tunzaa. `app/tasks/order_reminders.py` is a Celery task (see `app/core/celery_app.py`) for installment due-date reminders, run via `celery_worker` service / `celery -A app.core.celery_app worker`. Its T+24h scarcity nudge (`send_scarcity_nudge`) sends `WHATSAPP_REMINDER_TEMPLATE_NAME` (default `order_reminder`, registered in both `en` and `sw` under the same template name) with two body parameters built by `_order_reminder_components` — `order.product.name` (falls back to `"your order"` if the product's been deleted, since `product_id` is nullable) and `order.agreed_price` formatted with thousands separators (e.g. `45,000`). The language sent is `order.customer.language or settings.WHATSAPP_REMINDER_TEMPLATE_LANGUAGE` (default `en`) — `Customer.language` is classified exactly once, by the model itself during a normal WhatsApp conversation (`LLMService.generate_response` only asks for the one-shot `[LANGUAGE: en|sw]` marker in its system prompt while `customer.language is None`; parsed and persisted via `_parse_and_strip_language`, never re-classified afterward). This is WhatsApp-only by design — an Instagram-originated order (`Order.instagram_account_id` set instead of `account_id`) never reaches `send_scarcity_nudge` at all (`_account_for_order` returns `None` for it), so `generate_dm_response` doesn't classify language.

**Recurring subscription billing** (`Product.is_subscription`, `ProductSubscription`, `app/services/product_subscription.py`, `app/tasks/product_subscription_billing.py`): a product flagged `is_subscription=True` still closes its first sale through the normal one-time `Order`/`_dispatch_payment` flow, but `LLMService._create_subscription_if_needed` (called from `_close_deal`/`_close_instagram_deal`) also creates a linked `ProductSubscription` row (`PENDING_PAYMENT`). Once that first `order-<id>` Tunzaa callback comes back `COMPLETED`, `app/api/v1/tunzaa_webhook.py`'s `_activate_subscription_if_linked` flips it `ACTIVE` and schedules the first renewal; `FAILED`/`CANCELLED` instead flips it `PAYMENT_FAILED` via `_fail_subscription_if_linked` (no retry — the customer just has to ask Amara again, same as any other failed order). From month 2 on, billing is entirely self-rescheduling Celery (`charge_renewal.apply_async(countdown=...)`, mirroring the pre-existing `NumberSubscription`/`app/services/number_billing.py` pattern) — **there is no Celery Beat service in this stack**, only `celery_worker`, so any new recurring-billing feature needs this same self-rescheduling shape, not a cron-style periodic task. A renewal charge posts back to a `product-subscription-renewal-<id>` reference (routed separately from plain `order-<id>` refs in the webhook); failure retries up to `MAX_RENEWAL_RETRIES` (10, every `RENEWAL_RETRY_DELAY_SECONDS` = 36h) before `CANCELLED`. Renewal-failure/cancellation notifications enforce a single channel per subscription — whichever one the deal actually closed on (WhatsApp text via `Order.account`, or an Instagram DM via `ProductSubscription.instagram_customer_id`, which is only set for a deal closed over Instagram DM) — rather than broadcasting to every channel a customer might have used, since a business-initiated WhatsApp message outside an open session generally needs a pre-approved template anyway. Merchant visibility is dashboard-first (`OrderRead.subscription_status`/`subscription_next_billing_at`/`subscription_retry_count`, surfaced in the dashboard's Orders page), plus a best-effort WhatsApp push to the merchant's own number where they have a `WhatsAppAccount` — an Instagram-only merchant gets no merchant-side push (no "message the merchant" channel exists over Instagram; they're the account operator, not a DM peer of their own account), only the dashboard data.

**Access gating on Taskflow's own subscription** (`app/services/subscription_access.py`): separate from the generic billing mechanics above — this is specifically about a merchant paying *Taskflow itself* for the platform (not any merchant's own subscription product to their own customers). `settings.PLATFORM_SUBSCRIPTION_PRODUCT_SLUG` identifies which `Product` is "the" platform subscription (unset = gating off, nobody affected); `is_merchant_allowed_ai` resolves a `User` to a `Customer` by phone (`User.username` for OTP merchants, `User.phone_number` for accounts with no username — see the `/auth/me` PATCH endpoint) and checks that `Customer`'s `ProductSubscription` for the platform product: no subscription at all, `CANCELLED`, or `PAYMENT_FAILED` all deny; `PAST_DUE` gets a `PAST_DUE_ACCESS_GRACE_DAYS` (7-day) grace period before denying too, tracked via `ProductSubscription.past_due_since` (set once per past-due streak) and a self-scheduled one-off `check_past_due_grace_expired` task at exactly that deadline (retries alone don't line up with the 7-day mark, since they run on their own independent 36h cadence). "Denied" means `ai_enabled=False` on every account the merchant owns (Amara silent; dashboard/manual replies unaffected) via `sync_ai_access_for_merchant`, called from every subscription-status transition in `product_subscription.py` *and* every WhatsApp/Instagram account create/update/reconnect (`app/crud/whatsapp.py`, `app/crud/instagram.py`) — the latter is what stops a merchant from just re-toggling `ai_enabled` back on themselves, since the dashboard's WhatsApp settings form always sends `ai_enabled=true` on save. `product_subscription._resolve_merchant_for_platform_subscription` guards this whole path to only ever fire for the one configured platform product — a random merchant's own subscription product must never affect some other Taskflow user's `ai_enabled`, even if a `Customer` phone number happens to collide across them (`Customer` is global/not merchant-scoped in this schema).

`sync_ai_access_for_merchant` only runs when something *triggers* it — it never runs proactively just because `PLATFORM_SUBSCRIPTION_PRODUCT_SLUG` got set/changed in `.env`. Run `scripts/resync_subscription_access.py` once after changing that setting (including the first time it's configured) to force-evaluate every existing `User` immediately, rather than leaving pre-existing merchants on whatever `ai_enabled` they already had until something else happens to touch their account.

**Self-service billing for Taskflow's own subscription** (`app/services/self_service_billing.py`, `GET`/`POST /auth/me/subscription*`): the dashboard-native counterpart to the AI-negotiated flow — a merchant can view their own status and pay without going through Amara at all. `GET /auth/me/subscription` resolves the logged-in user's own `ProductSubscription` (reusing `subscription_access.find_platform_subscription`) and returns `status: null` if none exists yet, distinct from an explicit terminal status. `POST /auth/me/subscription/pay` ("Pay Now") always creates a *fresh* `Order`/`ProductSubscription` pair and dispatches a full-payment (no installments) Tunzaa push — deliberately the same flow whether this is a first-ever payment, catching up a lapsed `PAST_DUE` one, or resubscribing after `CANCELLED`, rather than trying to reactivate/branch on the old row. Activation happens exactly the same way as the chat-negotiated flow, through the normal `order-<id>` Tunzaa webhook path (`_activate_subscription_if_linked`) — Pay Now only replaces how the *first* charge gets initiated, not anything downstream of it. If no phone is on file (`User.username`/`phone_number`), the request accepts one inline and persists it via the same `set_user_phone_number` used by `PATCH /auth/me`, rather than requiring a separate trip to set it first.

**Instagram sales channel** (`app/api/v1/instagram.py`, "Instagram API with Instagram Login" — no Facebook Page involved, `graph.instagram.com` not `graph.facebook.com`): a merchant connects one Instagram professional account via OAuth (`/instagram/oauth/start` → Meta consent → `/instagram/oauth/callback`). `crud.instagram.upsert_account` enforces exactly one connected `InstagramAccount` per Taskflow user — reconnecting always replaces the prior row for that user, even with a different physical IG account, since Instagram's OAuth screen authorizes whichever account is active in the browser. The OAuth callback also calls `instagram_oauth.subscribe_to_webhooks`, which POSTs `subscribed_fields=comments,messages` to `/me/subscribed_apps` using the account's own token — the app-level webhook Callback URL/verify token configured once in the Meta dashboard is *not* sufficient on its own; each account must separately opt in or Meta never sends it events (an account connected before that field was added to the subscribe call is still only subscribed to `comments` until it reconnects). `POST /instagram/webhook` handles two independent event shapes via `InstagramWebhookParser`: `parse_inbound` (comments, `entry[].changes[]`) dispatches `process_inbound_comment` (public reply + one-shot private-reply DM, stateless, `app/services/llm.py`'s `generate_comment_reply`); `parse_inbound_messages` (DMs, `entry[].messaging[]`) dispatches `process_inbound_dm` (`app/tasks/instagram_dm_processing.py`), which tracks per-customer state via `InstagramCustomer`/`InstagramConversationContext` (reusing WhatsApp's `ConversationState` enum) and replies with `generate_dm_response`. Both parsers must filter out Meta's echoes of the connected account's own activity (`from.id == entry.id` for comments, `message.is_echo` / `sender.id == entry.id` for DMs) or Amara loops replying to herself forever — this caused a real production incident. Account matching depends on requesting `user_id` (not `id`) from `/me` — `id` is app-scoped and doesn't match webhook `entry[].id` (see `instagram_oauth.fetch_account_identity`). Unlike the comments webhook (which includes `from.username` directly), the messaging webhook only ever gives the sender's IGSID, so `InstagramCustomer.username` starts `None` for a DM-only customer — `handle_webhook`'s DM loop backfills it with a one-time `InstagramProvider.get_user_profile` lookup (`GET /{igsid}?fields=name,username`) the first time a customer with no username on file sends a message; a failed/errored lookup is swallowed (worst case the dashboard just keeps showing "Instagram user").

Unlike the one-shot comment reply, Instagram DM conversations are stateful and *can* close a real order — Instagram just never hands Amara a phone number the way WhatsApp does, so `generate_dm_response`'s prompt has her ask for one before emitting `[AGREEMENT_REACHED: ... phone=...]` (the WhatsApp prompt never includes `phone=`; the regex group is simply unmatched/`None` there). `LLMService._close_instagram_deal` then resolves/creates the same phone-keyed `Customer` the WhatsApp flow uses and reuses `_dispatch_payment`/`_schedule_reminders` as-is — the only real difference is the order gets `Order.instagram_account_id` set instead of `Order.account_id` (added specifically so an Instagram-only merchant, with zero `WhatsAppAccount` rows, can still have real orders — `crud/order.py`'s merchant-scoping queries outer-join both account tables and match on either one's `user_id`). `[HUMAN_HANDOFF]` is reserved for what the model genuinely can't/shouldn't handle (unreasonable customers, out-of-catalog questions, explicit request for a human) — a normal close no longer routes through it. Instagram has no API to message the account owner directly (only customers who've messaged the connected account — same limitation `notify_merchant` already has for subscription-renewal alerts), so an Instagram DM handoff is surfaced cross-channel instead: `LLMService._notify_merchant_of_instagram_handoff`. Both this and the WhatsApp-native `_trigger_human_handoff` alert go through a shared `_send_platform_alert_to_merchant` helper — sent via the **platform's own default WhatsApp credentials** (`settings.WHATSAPP_TOKEN`/`PHONE_NUMBER_ID`, the exact same ones `send_otp_message` uses), to `merchant.username or merchant.phone_number`, **not** via the merchant's own connected business `WhatsAppAccount`. This was a real production incident: the original design required `merchant.accounts` (a connected business `WhatsAppAccount`) and silently no-op'd when it didn't exist — and no `WhatsAppAccount` row existed anywhere in the database, so no alert had ever gone out. The fix reflects the actual mental model: a merchant's personal WhatsApp number is how they talk to Amara/Taskflow itself (same channel OTP already uses), completely independent of whichever *customer-facing* channels (a business WhatsApp number, Instagram) they've separately connected.

The alert itself is sent as the `handoff_notification` template (`WHATSAPP_HANDOFF_ALERT_TEMPLATE_NAME`/`WHATSAPP_HANDOFF_ALERT_TEMPLATE_LANGUAGE`, default `"en"` — merchant-facing, so one global default, same limitation as `WHATSAPP_OTP_TEMPLATE_LANGUAGE`), not free text — a second real production incident: a merchant essentially never has an open 24h WhatsApp session with the platform's own number (they only ever *receive* from it, never message it back), so a free-text send got a 200 OK from Meta's API on every attempt yet never actually reached the merchant's phone, silently dropped as an out-of-window re-engagement message. `handoff_notification` has a header (`"A customer {{customer}} needs your help right now."`) and body (`"They said: \"{{message}}\" / Reply directly using: /reply {{customer}} \"your message\""`) — note `{{customer}}` appears in **both** the header and body, so `_send_platform_alert_to_merchant` supplies it in both components' parameters, not just once. `_send_platform_alert_to_merchant` still logs the alert as a `Message` row for the dashboard's history view, but only if the platform's own number happens to also be connected as a real `WhatsAppAccount` (`phone_number_id == settings.PHONE_NUMBER_ID`) — the send itself never depends on that row existing. Unlike the WhatsApp-native handoff alert, the Instagram one doesn't also schedule the 15-minute reminder nudge — `app/tasks/handoff_reminders.py` resolves which account to alert from the customer's last *WhatsApp* message, which has no equivalent for an Instagram-originated handoff. Both handoff alerts quote the *customer's* own message (`_truncate_for_alert`, bounded to `HANDOFF_ALERT_MESSAGE_MAX_CHARS`, into the template's `{{message}}` variable), not Amara's reply — threaded through as `message_body` from each caller's own top-level param, not the `response_text`/`quote`-branch variable that used to be passed by mistake. The reply identifier (`{{customer}}`) is a bare phone number for WhatsApp or `@username`/`@ig_scoped_id` for Instagram (`_relay_to_instagram_customer` matches either, since a brand-new customer's display-name backfill may not have run yet) — matching the exact `/reply` syntax in the template's own static text (see `merchant_handler.py`'s `/reply` command below). Note `/reply`'s *inbound* side is still routed through a real `WhatsAppAccount` matching the sender to `account.owner.username` (`app/api/v1/whatsapp.py`) — for the merchant to actually use `/reply` by texting the platform's own number, that number needs to exist as a real `WhatsAppAccount` row (name `Taskflow`, matching `is_platform_account`), which is a one-time manual setup step, not automatic.

A human takes over a handed-off (or any) Instagram conversation from the dashboard: `GET /instagram/conversations` (every customer with at least one DM, most recent first), `GET /instagram/messages?customer_id=` (thread), `POST /instagram/messages/send` (manual reply via `InstagramProvider.send_direct_message`, works regardless of conversation state), `GET /instagram/handoffs` + `POST /instagram/handoffs/{customer_id}/resume` (WhatsApp's `/whatsapp/handoffs` equivalent, flips `HUMAN_HANDOFF` back to `NEGOTIATING`). Unlike WhatsApp's account resolution (header/query-param based, since one merchant can have many `WhatsAppAccount`s), these all resolve the account straight off the JWT via `get_instagram_account` — a merchant has at most one, and that dependency (along with `get_accounts_by_user`) only matches a row with a non-empty `access_token`.

`DELETE /instagram/accounts/{account_id}` disconnects — best-effort `instagram_oauth.unsubscribe_from_webhooks`, then `crud.instagram.disconnect_account` clears `access_token` to `""` and sets `ai_enabled=False`. It never deletes the `InstagramAccount` row itself: `InstagramCustomer`/`InstagramComment`/`InstagramDirectMessage`/`Order.instagram_account_id` all reference it via required FKs with no `ON DELETE CASCADE`, so a hard delete would break for any account with real history (unlike `DELETE /accounts/{id}` for `WhatsAppAccount`, which does hard-delete — that one has the same latent FK-violation risk for an account with existing messages/orders, just not one that's been hit yet). Reconnecting later (`upsert_account`) finds and revives the same disconnected row rather than creating a duplicate.

**DB layer**: single `app/db/models.py` (SQLAlchemy 2.0 `DeclarativeBase`) defines all models; no per-domain model files. `app/crud/*.py` holds one module per aggregate (`account`, `instagram`, `knowledge`, `message`, `product`, `user`, `whatsapp`) with plain functions taking a `Session` — no repository classes/ORM abstraction beyond that. `app/schemas/*.py` holds Pydantic request/response models, one file per domain, imported directly into the matching router.

**Config**: all runtime config is a single `pydantic-settings` `Settings` object in `app/core/config.py`, loaded from `.env` (see `.env.example` for the minimal required set, `.env.prod.example` for the full production set including R2 and Tunzaa). There is no per-environment settings class — `RUN_MODE=production` (checked in `scripts/run.sh`) toggles Gunicorn vs. `uvicorn --reload`, not settings.

## Notes for changes

- Language: WhatsApp-facing user copy (OTP messages, etc.) is written in Swahili in places (e.g. `auth.py`'s OTP message) — match this when touching customer-facing message text for the Tanzania merchant base.
- `WhatsAppProvider` (`app/core/provider.py`) is instantiated per-account with that account's own `access_token`/`phone_number_id`, except in the auth OTP flow which deliberately uses the platform-wide default credentials from `settings`.
- When adding a new merchant slash command, extend `handle_merchant_message` in `app/services/merchant_handler.py` — commands are matched by string prefix + regex, not a subcommand framework. `/reply [Phone|@instagram_username] [Message]` is the merchant's WhatsApp-native way to talk *to a customer* through their own WhatsApp number even for an Instagram-originated conversation — the `@` prefix disambiguates an Instagram username from a phone number (a real phone number never starts with `@`) and routes to `_relay_to_instagram_customer` instead of `_relay_to_whatsapp_customer`; neither path touches `ConversationContext`/`InstagramConversationContext` state (pure manual send, same as the dashboard's `POST /whatsapp|instagram/messages/send`) — the merchant still uses `/resume` separately once ready to hand back to Amara.
- Migrations live in `alembic/versions/`; some are named by revision hash (autogenerated) and some by hand-picked sequence names (`001_initial_migration.py`, `002_add_brokerage.py`) — check `alembic/versions/` history/heads before creating a new one rather than assuming linear numbering.
